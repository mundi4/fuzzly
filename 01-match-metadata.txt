# `match` 결과에 caller-side 스코어링을 위한 메타데이터 노출

## 배경

fuzzly 를 command-palette 류 UI 에 붙이다 보면 "결과를 어떤 순서로 보여줄 것인가" 문제가 반드시 따라온다. fuzzly 의 현재 출력 (`match` 가 `number[] | null`, `buildMatchRanges` 가 UTF-16 range 배열) 만으로는 호출자가 직관적인 스코어링을 만들기 어렵다.

## 제안의 전제 — fuzzly 가 직접 스코어링하면 안 되는 이유

먼저 "fuzzly 가 score 를 내놓으면 되지 않나" 는 안 되는 방향이라고 본다. 이유:

1. **스코어링은 UX 정책이지 알고리즘이 아님.** 앱마다 "좋은 매치" 의 정의가 다르다. 파일명 검색은 prefix 매치가 최고, 노트 앱은 단어 경계 매치가 최고, 어떤 앱은 favorite/pinned/recency 같은 **fuzzly 가 알 수 없는 외부 신호** 가 지배적이다.
2. **외부 prior 와 충돌.** 예를 들어 노트 앱은 `updatedAt desc` 라는 매우 강한 기본 순서를 이미 가진다. fuzzly 가 자체 스코어로 재정렬하면 이 신호를 덮어써서 오히려 UX 가 나빠진다. 매 키스트로크마다 순서가 바뀌면 `activeIndex` 추적, 시선/muscle memory 가 모두 깨진다.
3. **fuzzly 의 비교 우위는 매칭 알고리즘**(한글 초성/중성/종성 decompose + tail spillover) 이다. 스코어링은 누구나 짤 수 있는 것이라 fuzzly 가 이걸 내장한다고 차별화될 영역이 아니다.

결론: **정책은 호출자에게 맡기되, 호출자가 정책을 만들 수 있을 만큼의 신호를 fuzzly 가 내놔야 한다.**

## 현재 정보로 가능/불가능한 신호

스코어링에 쓰기 좋은 시그널을 호출자 관점에서 분류:

| 신호 | 현재 얻는 방법 |
|---|---|
| 첫 매치가 target 맨 앞? | `ranges[0].start === 0` ✅ |
| 단어 경계(`_`, 공백, case 전환) 직후 매치? | 호출자가 `target[range.start - 1]` 을 다시 검사해야 — UTF-16 인덱스라 grapheme 경계 고려 필요, 번거로움 |
| 매치가 연속적인가 (한 덩어리 vs 흩어짐)? | `ranges.length` 로 간접 유추만 가능 |
| 초성만으로 매치 vs 완성글자 매치? | **현재 얻을 수 없음** — `match` 가 내부에서는 알지만 리턴에서 버림 |
| 매치에 몇 개 query grapheme 이 소모됐나 / 얼마나 먼 거리로 spill 됐나? | **현재 얻을 수 없음** |

내부 상태머신(`match.ts`) 은 이 정보를 이미 계산하고 있으므로 **알고리즘 변경 없이 return 필드 확장만** 으로 해결된다.

## 구체적 제안

`match` 의 리턴을 확장:

```ts
export type MatchInfo = {
  /** 기존 match 의 반환값과 동일 — 매치된 target grapheme 인덱스 */
  indices: number[];

  /** 매치가 target 0 번째에서 시작했는가 */
  startsAtZero: boolean;

  /**
   * 단어 경계 직후에서 시작한 매치의 수.
   * 경계 정의는 target 의 이전 grapheme 이 whitespace/underscore/hyphen/dot 이거나,
   * lowercase→Uppercase 전환인 경우.
   */
  boundaryHits: number;

  /**
   * 연속된 run 의 수. indices 가 [3,4,5,10,11] 이면 runs=2.
   * 값이 작을수록 매치가 한 덩어리에 모여 있음.
   */
  runCount: number;

  /**
   * 이 매치에서 모든 query grapheme 이 초성만으로 매칭됐는가.
   * true 면 사용자가 "대충 친" 상태, false 면 완성글자 매치가 더 많음.
   */
  initialConsonantOnly: boolean;
};

export function match(
  query: Query,
  target: Target,
  options?: MatchOptions,
): MatchInfo | null;
```

`buildMatchRanges` 는 호환 유지 (기존 `indices: number[]` 계약만 필요).

## 호출자 예시

```ts
// 노트 앱 — updatedAt desc prior 유지하면서 prefix/boundary 만 살짝 위로.
function scoreFor(info: MatchInfo): number {
  let s = 0;
  if (info.startsAtZero) s += 1000;
  s += info.boundaryHits * 100;
  s -= info.runCount * 5;          // 흩어진 매치 페널티
  if (info.initialConsonantOnly) s -= 20;  // 약한 매치
  return s;
}
```

이 10 줄이면 대부분의 consumer 가 자기 앱에 맞는 랭킹을 만들 수 있다. fuzzly 자체는 policy-free 유지.

## 대안 — 기본 score utility 동봉

원한다면 `fuzzly/score` 같은 분리된 entry 로 `defaultScore(info: MatchInfo): number` 를 옵션 유틸로 제공 가능. 핵심 import 에는 들어가지 않으니 dead code elimination 으로 안 쓰는 앱은 무료.

## 우선순위 근거

이 하나가 대부분의 "팔레트 UX 에서 fuzzly 가 덜 쓰기 좋다" 는 체감의 원인이다. 알고리즘 재설계가 아니라 **이미 `match.ts` 가 알고 있는 상태를 리턴 타입에 실어주는 변경**이므로 작업량 대비 임팩트가 제일 크다.
